# Розробка й перевірка СВОЯ

React 19, TypeScript 5, Vite 6, supabase-js 2; точні встановлені версії зафіксовані у package-lock.json. Публікація — GitHub Pages, префікс `/-svoya/`. Чинні компоненти — `src/site/`; попередня реалізація `src/pages/` не підключена до маршрутизатора.

## Ізоляція від PORUCH

Спільний робочий Supabase не є тестовим середовищем. Команди нижче використовують тільки каталог `supabase-svoya`, локальні порти 55420–55424 і нову порожню базу. Нічого не лінкуйте до хмарного проєкту. Не запускайте `supabase db push` із кореня репозиторію.

`supabase/migrations/` містить змішані історичні міграції. Їх не змінено й не оголошено узгодженими з історією спільного проєкту. Файли `docs/original-db/` — знімки для відновлення, не інструкція запускати SQL на робочій базі.

## Локальний запуск

Потрібні Node >=22.13, npm і Docker/Podman для повного Supabase. Команди запускаються з кореня репозиторію:

```bash
npm ci
npm run local:start
npm run local:env
npm run dev
```

Відкрийте `http://127.0.0.1:5173/-svoya/club/`. Локальна пошта — `http://127.0.0.1:55424`: листи нікуди не доставляються. Команда `npm run local:stop` зупиняє контейнери. Тестові дані не призначені для перенесення до production.

`local:env` читає статус лише цього локального стенда та записує в ігнорований `.env.local` адресу й **публічний** anon key. Service-role key не записується до браузерного оточення. Не копіюйте робочі ключі або дані у стенд.

Обов’язкові змінні: `VITE_SVOYA_ENV=local|test|production`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. `.env.production` містить публічну конфігурацію чинного сайту. Захист у клієнті відмовляє локальному перегляду в підключенні до спільної робочої бази. Це запобіжник від помилок розробки; захист даних забезпечують серверні RLS та grants.

Якщо `.env.local` існує, Vite використовує його і під час локальної production-збірки. Для справжнього релізу CI збирає чистий checkout без `.env.local`. `npm run preview` із робочою конфігурацією навмисно не підключає клуб до production з localhost; для перевірки використовуйте локальний стенд.

## Міграції

`supabase-svoya/supabase/migrations/20261009104241_svoya_baseline.sql` — канонічна початкова схема **тільки для порожньої бази**. Вона відтворює SVOYA із перевірених джерел коміту `6d586d5c49af3a25e6f4aba67dd04106653fb0ab`; перелік — `supabase-svoya/BASELINE_SOURCES.json`. В ній немає користувачів, ключів push або об’єктів PORUCH.

`20261009104307_svoya_greeter_consistency.sql` — окреме виправлення призначення зустрічаючої. Перепризначає недоступну учасницю на доступну організаторку, інакше очищає призначення; обробляє скасування, відхилення, блокування, призупинення членства та відмову зустрічати новеньких. Виправляє також старі некоректні призначення.

Для майбутнього застосування до робочої бази потрібне **окреме погодження саме вузького виправлення**, попередня перевірка версії `svoya_private.community_action`, тригерів та резервної копії. Не застосовуйте baseline до існуючої бази, не ремонтуйте історію shared-проєкту навмання. Деплой фронтенду не застосовує SQL. У поточній роботі production SQL не запускався.

Нову локальну міграцію створюйте CLI:

```bash
npx supabase migration new descriptive_name --workdir supabase-svoya
```

## Перевірки

| Команда | Що перевіряє | Межі |
|---|---|---|
| `npm test` | Шляхи Pages, service worker, ICS, добірки, ізоляцію конфігурації, вихід, пагінацію, відхилену заявку, модерацію, оновлення запрошень, гонку запитів каталогу | React/jsdom і керовані відповіді API; це не перевірка браузерної верстки |
| `npm run test:db` | Повний новий ланцюжок міграцій, RLS, права, приватний чат, місткість, чергу, нагадування, призначення зустрічаючої | PGlite/PostgreSQL; Auth identity, Storage metadata й cron замінені локальними заглушками; мережа заборонена |
| `npm run test:integration` | Реальні локальні Auth, перехоплені email, PostgREST, Storage, RLS і сценарії участі | Потребує запущеного Docker-стенда; відмовляється працювати з remote URL |
| `npm run typecheck` | TypeScript | Не доводить працездатність API |
| `npm run build` | Production bundle + прямий `/club/` і 404 fallback | Не доводить працездатність серверних сценаріїв |
| `npm audit --audit-level=moderate` | Відомі вразливості дерева npm | Не заміняє аудит коду та контейнерів |

`Verify SVOYA` запускає перевірки на PR і гілках `fix/**`, включно з Docker-стендом без секретів репозиторію. `Deploy SVOYA` перевіряє тести, SQL та типи перед збіркою `main`.

## Що залишається перевірити перед відкритим запуском

- Погодити й застосувати тільки вузьке SQL-виправлення зустрічаючих після перевірки стану shared-бази.
- Перевірити доставку production SMTP і дозволені redirect URL на спеціальних тестових акаунтах, не на учасницях.
- Перевірити системні push та відкриття посилань на Android/iOS після надання дозволу. Локальні тести їх не надсилають.
- Візуально перевірити реальний мобільний браузер, клавіатуру, модальні вікна й екранну клавіатуру.
- Окремо вирішити продуктову політику публічних фото історій: bucket `svoya-community` публічний; модерація запису не робить вже завантажений файл приватним. Ця політика тут не змінена.

## Браузерні перевірки

На запущеному локальному стенді: `npx playwright install chromium webkit`, потім
`npm run test:browser`. Налаштування Playwright саме читає публічний ключ локального
стенда й запускає окремий Vite на 5173; порт має бути вільним. Зовнішню мережу в
браузерних тестах заблоковано. Ключ адміністратора не передається браузеру.

CI запускає ті самі сценарії в Chromium і WebKit на десктопному та мобільних
розмірах. Артефакт `svoya-browser-report` містить знімки та звіт. Додано також
одночасні заявки через справжній PostgREST та перевірку відкоту SQL-схеми.
Деталі й межі робочих перевірок: [RELEASE_2026-10-09.md](RELEASE_2026-10-09.md).
